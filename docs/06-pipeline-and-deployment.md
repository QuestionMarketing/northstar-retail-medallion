# 06 Pipeline, deployment and the Fabric CLI

Code: [`tools/mkpl.py`](../tools/mkpl.py), [`tools/build_nb.py`](../tools/build_nb.py), [`tools/upd.py`](../tools/upd.py)

## Notebook source format
Notebooks are authored as plain `.py` files with `# %%` cell markers (`# %% [markdown]` for text). Benefits: real diffs in Git, editable in any IDE. `build_nb.py` converts them into Fabric's notebook item format (`notebook-content.py` plus `.platform`), binding the default lakehouse. Then:

```powershell
fab import "Retail_VS.Workspace/NB_02_Silver_Clean.Notebook" -i out\NB_02_Silver_Clean.Notebook -f
fab job run "Retail_VS.Workspace/NB_02_Silver_Clean.Notebook"
```

## The pipeline
`PL_Retail_Medallion` is four `TridentNotebook` activities in a chain, each `dependsOn` the previous with condition `Succeeded`:

```
Bronze_Ingest -> Silver_Clean -> Gold_Model -> Gold_Churn
```
Policy: timeout 12 h, retry 0, 30 s retry interval. The pipeline JSON is generated by `mkpl.py` (notebook IDs and workspace ID are parameters at the top) and deployed with `fab import`.

Design notes:
* **Fail fast, do not retry blindly.** Retry 0, because a deterministic failure (a bad rule) will fail again; transient errors are better handled by re-running.
* Because every notebook ends with `notebookutils.notebook.exit(...)`, the exit value is visible in the monitoring hub and can drive an `If Condition` on `gold_ok`.
* **Honest status:** the notebooks were each run and validated individually during the build. The pipeline was deployed and structurally validated; a scheduled end-to-end run is the next step for production. Add a schedule trigger and an alert (email/Teams) on failure.

## Fabric CLI cheat-sheet (what I actually used)

```powershell
fab auth login                                   # interactive sign-in
fab ls                                           # list workspaces
fab ls "Retail_VS.Workspace"                     # list items
fab get "Retail_VS.Workspace/retail_lakehouse.Lakehouse" -q properties.sqlEndpointProperties
fab table schema "Retail_VS.Workspace/retail_lakehouse.Lakehouse/Tables/gold/fct_order_line"
fab import <path> -i <local folder> -f           # create/overwrite an item from its definition
fab api -A powerbi -X post "datasets/<id>/executeQueries" -i q.json   # run DAX
fab api -X post "workspaces/<ws>/reports/<id>/updateDefinition" -i body.json
```

## Gotchas worth remembering

1. **`fab api -i` wants a file** when the JSON is non-trivial (PowerShell mangles inline quotes).
2. **`fab import` for a report returned "imported" but changed nothing.** Use `updateDefinition` (long-running: HTTP 202, then poll until Succeeded). `upd.py` does this.
3. **Definition parts are base64.** Each file in the `.Report` folder becomes `{path, payload: base64, payloadType: InlineBase64}`.
4. **Trial capacity limits.** Data Agents and Copilot returned `UnsupportedCapacitySKU` on a trial (FTL64) capacity. Check capacity before promising a feature.
5. **Tenant policies bite.** Export-to-image was disabled; plan screenshots another way.
6. **Never commit tokens.** `fab` keeps credentials in the OS credential store, nothing in the repo.

## Git for Fabric
For a production team: connect the workspace to a Git repo with Fabric's Git integration (Azure DevOps or GitHub). Notebooks, pipelines, models and reports are all text-defined items, so the whole workspace round-trips. Pair with deployment pipelines (Dev, Test, Prod) and parameterise the workspace/lakehouse IDs that are hard-coded in these scripts.

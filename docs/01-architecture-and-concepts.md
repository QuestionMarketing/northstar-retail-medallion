## 1. What problem does a medallion architecture solve?

Raw operational data is unfit for analytics: inconsistent formats, duplicates, missing keys, mixed grain. If analysts query it directly, every report re-implements (differently) the same cleaning, and numbers never agree.

A **medallion architecture** pushes data through progressively more trusted layers, each with ONE job:

| Layer | Question it answers | Allowed to change data? | Typical consumers |
|---|---|---|---|
| **Bronze** | "What exactly did the source send us, and when?" | No. Only append lineage | engineers, audit, replay |
| **Silver** | "What is the clean, typed, deduplicated version of each entity?" | Yes: parse, type, standardise, dedupe, resolve | data scientists, engineers |
| **Gold** | "What does the business measure, in a shape that is fast and unambiguous?" | Yes: model, aggregate, enrich | BI, semantic models, apps |

Why it works:
* **Replayability.** Bronze is the untouched copy. If a cleaning rule is wrong you fix Silver and re-run, you do not re-extract from the source.
* **Separation of concerns.** Parsing bugs live in Silver, business logic bugs in Gold. You know where to look.
* **Auditability.** Lineage columns (`source_file`, `batch_id`, `ingestion_timestamp`) travel with every row, and every layer reconciles to the one before.

## 2. The Fabric components and why each was chosen

| Component | Used for | Why this and not something else |
|---|---|---|
| **Lakehouse** (`retail_lakehouse`) | Storage of files (`Files/landing`) and Delta tables (`Tables/<schema>/...`) | One OneLake copy serves Spark, SQL endpoint and Direct Lake. Schemas `bronze`, `silver`, `gold` give the layers physical separation |
| **Delta Lake** | Table format | ACID writes, schema evolution (`overwriteSchema`), time travel, and it is what Direct Lake reads |
| **Spark notebooks (PySpark)** | All transformations | Files are large (100MB JSONL) and need nested-JSON handling and ML. Spark does both in one engine |
| **Data Pipeline** | Orchestration (`PL_Retail_Medallion`) | Sequential dependency Bronze to Silver to Gold to Churn, with retry/timeout policy and monitoring |
| **Materialized Lake View** | `gold.mlv_daily_channel_sales` | Declarative, auto-refreshed aggregate. Falls back to a plain table if the feature is unavailable (the notebook handles both) |
| **Direct Lake semantic model** | BI layer | Reads Delta files directly: import-like speed without a scheduled refresh copy |
| **PBIR report** | Presentation | Text-based report format: diffable, generated by code, version-controllable |
| **Fabric CLI (`fab`)** | Deploy and inspect everything from a terminal | Reproducible; the opposite of click-ops |

## 3. Design principles used throughout

1. **Each layer reconciles to the previous one.** Row counts and £ totals are asserted, not eyeballed (`notebooks/01_bronze.py` last cell, `notebooks/03_gold.py` DQ section).
2. **Fail loudly.** Bronze `assert`s counts equal the client's inventory. Gold exits with `gold_checks_failed: [...]` if any check fails, so a pipeline run goes red.
3. **Keep the original value next to the cleaned one** (`sku_raw`, `crm_customer_id_raw`, `store_code_raw`). When someone disputes a join, you can show why.
4. **Surrogate keys in Gold, business keys in Silver.** Gold keys are integers (small, fast joins); Silver keeps the readable `C0001234`.
5. **Unknown members, not NULL keys.** Guest sales map to `customer_key = -1` ("Unknown customer") so facts never lose rows in a join.
6. **Document every assumption in the artefact itself** (the markdown cells in the notebooks, the About page in the report).
7. **Idempotent writes.** `mode("overwrite")` + `overwriteSchema`: re-running a notebook gives the same result.

## 4. The data model (Gold)

Star schema, one fact table, four dimensions, one extension table:

```
dim_date ──┐
dim_product ──┤
dim_store ──┼── fct_order_line (grain: one row per order line, POS + e-commerce)
dim_customer ─┘            ▲
        ▲                  └── dim_store (second, inactive role: fulfilment_store_key)
        └── customer_churn_score (1 row per scored customer)
```

**Grain** is the first thing to decide. Ours: *one commercially reportable order line*. Returns are negative lines with `is_return = true`. Cancelled web lines are excluded from the fact (counted in DQ).

**Conventions** (written in the notebook header and enforced by checks):
* `unit_price` = pre-discount, ex-VAT
* `net_sales` = ex-VAT, after discount
* `gross_sales` = inc-VAT, after discount
* `net + vat = gross` (a DQ check proves it to within 1p)

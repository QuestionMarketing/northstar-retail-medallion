# 04 Semantic model and report

Code: [`tools/mkmodel.py`](../tools/mkmodel.py), [`tools/mkreport2.py`](../tools/mkreport2.py), [`tools/lint.py`](../tools/lint.py), [`tools/upd.py`](../tools/upd.py)

## Why generate the model and report with code?
Power BI artefacts are just text: **TMDL** for the semantic model, **PBIR** (JSON) for the report. Generating them with Python gives you repeatability, review-able diffs, and the ability to restyle 140 visuals by changing one function. The trade-off: you must know the formats. The notes below are what I learned the hard way.

## Semantic model (`mkmodel.py`)

### Direct Lake
Each model table is a Direct Lake *entity partition* over a Gold Delta table:

```
partition Sales = entity
    mode: directLake
    source
        entityName: fct_order_line
```
with a shared `expression DatabaseQuery` pointing at the lakehouse SQL endpoint. Columns are discovered from the live Gold schema (`fab table schema`), so the model follows the data.

| Mode | Data copy | Refresh | Latency | Use when |
|---|---|---|---|---|
| Import | yes (in model) | scheduled | fast queries | small/medium data |
| DirectQuery | no | none | slower, source-bound | must be live and source is fast |
| **Direct Lake** | no (reads Delta/Parquet from OneLake) | metadata "reframe" | import-like | Fabric lakehouse/warehouse, big data |

### Relationships (star schema)
* `Sales[customer_key/product_key/store_key/date_key]` many-to-one to the dimensions.
* `Sales[fulfilment_store_key]` to `Store` is a second relationship, **inactive** (role-playing). Use it in a measure with `USERELATIONSHIP` when you want "by fulfilment store".
* `Churn[customer_key]` one-to-one to `Customer`, both directions, so churn slicers filter customers and vice-versa.

### Measures (40+)
Core: `Net Sales`, `Gross Sales`, `Orders` (`DISTINCTCOUNT`), `Return Rate`, `Discount %`, `Avg Order Value`, `Online Share %`.
Time: `Net Sales PM` (`DATEADD`), `Net Sales MoM %` (explicit month window with `ALL('Date')`, because the dataset is only three months), running total with `ALLSELECTED`.
Churn: `Customers Scored`, `High-Risk Customers`, `Revenue at Risk`.
Always `DIVIDE()`, never `/`, so divide-by-zero returns blank rather than an error.

### Dynamic narratives: the consulting trick
Under each page are "What's happening" and "Recommended action" boxes that **change with the slicers**. They are ordinary DAX measures building a sentence:

```DAX
"Net sales of " & FORMAT([Net Sales]/1e6,"£0.0")&"M from " & FORMAT([Orders],"#,0") & " orders ..."
& " Latest month is " & FORMAT([Net Sales MoM %],"+0.0%;-0.0%") & " vs the prior month."
```
Recommendations are `IF` rules on thresholds (e.g. return rate above 3% triggers "review worst departments"). Helper generators (`top()`, `topv()`, `M()`, `P()`) in `mkmodel.py` build "top X by measure" phrases with `TOPN`. This is rules-based commentary, not an LLM, which is a feature: it is deterministic, auditable and free.

## The report (`mkreport2.py`)

### PBIR structure
```
Report.Report/definition/
  report.json, version.json
  pages/pages.json            # order + active page
  pages/<pageId>/page.json
  pages/<pageId>/visuals/<visualName>/visual.json
```
Everything is generated by a tiny `Page` class with helpers (`bar`, `tree`, `funnel`, `scat`, `donut`, `ribbon`, `waterfall`, `combo`, `kpis`, `slicers`, `insight`). A page is declared as rows of `(name, visualType, weight, roles, title, sort)`; the **grid layout engine** divides width by weight and height by rows, so nothing overlaps by construction.

### Design decisions
* Hierarchy: filters, then 6 KPI cards, then charts, then narrative band (the "3-30-300" idea: glance, scan, study).
* Visual variety on purpose: treemap, funnel, donut, ribbon, waterfall, bubble scatter, combo, gauge; one table only (win-back list). Right chart for the question, not just bars.
* Typography restricted to 8 pt and 9 pt (a stakeholder request) to prevent crowding; applied in the theme and per visual.
* Month is a dropdown slicer and Channel a tile slicer, both **synced across pages** via `syncGroup`.
* A `lint.py` check validates bounds and overlaps before every deploy (target: 0 issues).

### Things that did NOT work (save yourself the time)
| Attempt | Result | What I did |
|---|---|---|
| Measure-bound textbox runs | report hung on load | one-cell `tableEx` with the header hidden by matching colours |
| Native forecast on the line chart | never rendered in the service | replaced with a trailing 28-day run-rate and an explicit "not a statistical forecast" note |
| `fab import` of the report | said "imported" but changed nothing | call the REST `updateDefinition` API directly (`tools/upd.py`) |
| Pasting JSON into `fab api -i` from PowerShell | quoting errors | write the body to a file and pass `-i file.json` |
| Image export API | disabled by tenant policy | screenshots via a browser instead |

### Q&A page
A native `qnaVisual` plus a "try asking" panel. This is Power BI's built-in natural-language engine (not an LLM). For LLM answers you need Copilot or a Fabric Data Agent, which require a paid capacity (see doc 08). Meanwhile, the same model can be queried with DAX through the `executeQueries` REST API or the FabricIQ MCP server.

## Deploy loop
```
python tools/mkreport2.py   # generate PBIR
python tools/lint.py        # 0 issues or stop
python tools/upd.py         # base64 parts -> POST .../reports/<id>/updateDefinition (202 -> Succeeded)
```
Then screenshot every page and look at it. Valid JSON does not mean it renders.
